# IA no Pipeline — Integração com Claude API

> **Stack**: Anthropic SDK (`@anthropic-ai/sdk`) · claude-sonnet-4-6 · output estruturado com Zod
>
> Spec completa: [`specs/06-ai-integration-spec.md`](../specs/06-ai-integration-spec.md)

---

## Princípios de Design

1. **Output sempre estruturado**: Claude retorna JSON validado por Zod — nunca texto livre parseado com regex
2. **Prompts versionados**: cada endpoint tem seu próprio arquivo de prompt em `api/src/ai/prompts/`
3. **Graceful degradation**: falha no AI (`ANTHROPIC_API_KEY` ausente, rate limit, timeout) retorna erro HTTP claro sem afetar as outras rotas
4. **Custo visível**: tokens de input e output logados por request (`app.log.info({ ...usage })`)
5. **Tamanho controlado**: requests acima de 50kB são rejeitados com `413` antes de chamar a API

## Endpoints

### POST /ai/analyze-inconsistencies

**Persona**: Engenheiro GIS sênior analisando qualidade de dados de uma rede elétrica.

**Input**: saída do `GET /inconsistencias` (resumo + amostras das 5 regras VR-001→005)

**Output estruturado**:
```json
{
  "severity_assessment": "string",
  "top_priorities": [
    {
      "rank": 1,
      "rule": "VR-001",
      "count": 3000,
      "recommendation": "Revisar postes sem subestação associada na região norte",
      "sql_hint": "SELECT id FROM rede_eletrica.postes WHERE NOT EXISTS (...)"
    }
  ],
  "patterns_detected": ["Concentração de VR-001 na bbox [-50,-25,-49,-24]"],
  "next_steps": ["Executar script de correção para VR-005 (SRID)"]
}
```

**Regra de priorização**: `rank` calculado por `count × peso_severidade` (HIGH=3, MEDIUM=2, LOW=1)

### POST /ai/benchmark-insights

**Persona**: Engenheiro de performance comparando SQL Server 2022 vs PostGIS 3.4.

**Input**: saída do `POST /benchmark/run` (p50/p95/p99 por cenário por banco)

**Output estruturado**:
```json
{
  "executive_summary": "string",
  "tradeoff_analysis": {
    "sql_server_wins": ["B09"],
    "postgis_wins": ["B01", "B07", "B12"],
    "key_insight": "PostGIS domina workloads de JOIN e KNN; SQL Server é competitivo em filtros mistos"
  },
  "optimization_suggestions": [
    {
      "applies_to": "sqlserver",
      "scenario": "B07",
      "suggestion": "Substituir STDistance < r por STIntersects com STBuffer para forçar uso do índice",
      "expected_improvement": "30–50% em regiões densas"
    }
  ],
  "cost_analysis": {
    "note": "Licença SQL Server Enterprise adiciona ~$15k/ano vs PostGIS (gratuito)",
    "break_even": "Acima de 5M features, vantagens de suporte empresarial podem justificar custo"
  }
}
```

### GET /ai/query-suggestions?scenario=B07

**Persona**: Otimizador de queries espaciais com few-shot calibration.

**Input**: query param `scenario` (B01–B15) — lê `benchmark/scenarios.json` automaticamente

**Output estruturado**:
```json
{
  "scenario": "B07",
  "suggestions": [
    {
      "database": "sqlserver",
      "current_query": "SELECT TOP 1000 p.id, t.id FROM postes p JOIN trechos t ON p.geom.STDistance(t.geom) < 0.005",
      "optimized_query": "SELECT TOP 1000 p.id, t.id FROM postes p JOIN trechos t ON p.geom.STIntersects(t.geom.STBuffer(0.005)) = 1",
      "explanation": "STDistance sem índice força full scan; STIntersects com STBuffer aproveita GEOMETRY_AUTO_GRID",
      "estimated_improvement": "2–4× em datasets > 50k features"
    },
    {
      "database": "postgis",
      "current_query": "SELECT p.id, t.id FROM postes p JOIN trechos t ON ST_DWithin(p.geom, t.geom, 0.005) LIMIT 1000",
      "optimized_query": "SELECT p.id, t.id FROM postes p JOIN trechos t ON p.geom && ST_Expand(t.geom, 0.005) AND ST_DWithin(p.geom, t.geom, 0.005) LIMIT 1000",
      "explanation": "Adicionar && com ST_Expand força uso do índice GIST antes do predicado exato ST_DWithin",
      "estimated_improvement": "10–20% em regiões densas via two-pass index scan"
    }
  ]
}
```

## Implementação

### Fluxo de uma Chamada

```
POST /ai/analyze-inconsistencies
  1. Zod parse do body (mínimo: { summary: {} })
  2. Verifica tamanho (< 50kB)
  3. claude-client.ask(SYSTEM_PROMPT, userMessage, InconsistencyAnalysisSchema)
     a. getClient() → Anthropic singleton (valida ANTHROPIC_API_KEY)
     b. AbortController timeout 30s
     c. messages.create(model, system, messages)
     d. Em 429: espera retry-after, tenta uma vez
     e. Em 5xx: AiUpstreamError → HTTP 502
     f. JSON.parse(content[0].text)
     g. Zod.parse → AiInvalidResponse se falhar → HTTP 500
  4. app.log.info({ input_tokens, output_tokens })
  5. Retorna { ...result, _meta: { model, input_tokens, output_tokens } }
```

### Mapa de Erros HTTP

| Situação | HTTP | Código |
|----------|------|--------|
| `ANTHROPIC_API_KEY` ausente | 500 | `AI_NOT_CONFIGURED` |
| Rate limit (429) após retry | 429 | `AI_RATE_LIMITED` |
| Claude API 5xx | 502 | `AI_UPSTREAM_ERROR` |
| JSON ou Zod inválido | 500 | `AI_INVALID_RESPONSE` |
| Timeout > 30s | 504 | `AI_TIMEOUT` |
| Body > 50kB | 413 | `REQUEST_TOO_LARGE` |

## IA no Processo de Engenharia

Além dos endpoints de produto, este projeto usa IA também no processo:

| Ferramenta | Quando é invocada |
|-----------|-------------------|
| `.claude/agents/reviewer.md` | Revisão de código antes de todo PR |
| `.claude/agents/po.md` | Validação de escopo antes de cada sprint |
| `.claude/agents/qa.md` | Checklist antes de merge |
| `.github/workflows/ai-pr-review.yml` | Review automático via GitHub Actions em todo PR |
| `/project:benchmark` | Slash command que roda benchmarks + chama `/ai/benchmark-insights` |
| `/project:validate` | Slash command que roda validação + chama `/ai/analyze-inconsistencies` |

Ver [ADR-005](adr/005-ia-no-pipeline.md) para a justificativa arquitetural desta abordagem.
